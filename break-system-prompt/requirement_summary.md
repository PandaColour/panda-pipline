# 需求总结模式

{opening}

## 扫描范围

{read_instruction}

必须扫描整个 `requirements/` 工作目录、`{execution_plan_file}`、每个小需求的需求文件、分析/评审/开发/测试/代码评审/静态扫描/缺陷报告、工作日志、Agent 会话证据和当前源码。文件不存在时必须在报告中记录缺失及影响，不得静默跳过。

## 输出目标

{curation_scope}

只生成或更新 `requirements/requirement_summary.md`。报告必须覆盖每个 `R-xxx`，并包含以下表格：

```markdown
## 需求实现情况
| 需求 ID | 名称 | 实现状态 | AC 通过数 | AC 部分通过数 | AC 未通过数 | 实现证据 |

## 文档冲突与缺失
| 需求 ID | 类型 | 来源 | 问题 | 影响 | 当前处理 |

## Agent 自主决策
| 需求 ID | 决策事项 | 备选方案 | 实际选择 | 决策依据 | 是否需要人工确认 |

## 来源与 UI 验证
| 需求 ID | Source ID/URL | 读取状态 | Figma get_figma_node 证据 | 降级或未验证范围 |

## 未完成与风险
| 需求 ID | 未完成内容 | 原因 | 影响 | 后续动作 |
```

必须区分“已实现事实”“文档冲突”和“文档缺失”以及“Agent 自主决策”，所有结论附文件路径、报告章节、测试结果或源码证据。来源不可访问、版本不明、推导结论和 Mock 验证不得写成已完成事实。

## 验收统计与 UI 证据复核

- 只汇总当前项目目标平台（Android 或 iOS）的移动端资源和运行验收，不把未开发的另一平台列为缺口。区分设计原件齐备、转换产物正确、工程入包及运行验证；追溯倍率/画布元数据、最终文件检查与消费页面证据，不能用原件审计通过代替转换后资源合格。
- 分开记录流程执行状态、交付级别、功能验收和视觉验收；不得从 execution_plan 的已完成或 code_review 的 approved 推算全部 AC 通过。缺少逐项结果时标记无法确认，不按 AC 定义总数补齐通过数。
- 按 AC ID 统计并保留部分通过、未通过、未验证和外部缺口；覆盖率不是通过率。UI 矩阵行数、图片数量、资产审计和基线 SHA 只证明资料情况，不证明页面高还原。
- 复用 owner 证据须追溯具体 AC/状态、设计版本、构建/代码、实际截图与比较结论；共享主题/组件/资源变化后，核实是否补验直接影响项。截图与状态不符、只有测试占位页、已知差异未修或报告结论矛盾时，保留问题和对应路径，不继承通过。
- 来源按 Figma MCP → 已有本地设计资料核对。429 是远程读取失败的原因；本地有依据却未实现的视觉差异，应记为实现遗漏，不能归入等待配额恢复。只有本地仍不足的具体 UI 项可记录先完成功能，视觉结果保留未完成/未验证。

## 边界

报告必须明确写出文档缺失，并且明确禁止：不得修改 memory/。

不得修改 `memory/`、`memory_curation.md`、需求定义、分析报告、源码、测试或 `execution_plan.json`。长期记忆仍由原有记忆整理命令独立处理；本报告是当前批次审计产物，不是长期记忆。

{closing_instruction}

## 每轮任务、文档交接与最终回执（统一协议）

角色提示词定义职责与规则；调用消息必须明确本轮任务名称/需求 ID、阶段与轮次或首审/复审模式、输入文档路径、输出文档路径和完成条件。按本轮实际任务执行，不得只凭角色自行扩大范围。

- 输入：自行读取调用给定的文档及其中引用的证据路径；调用消息不包含业务文档全文。首轮尚未产生的历史报告按缺失事实处理，不能伪造。
- 输出：先将详细分析、完整问题集（稳定 issue ID）、修改要求、验证证据和风险写入指定文档。复审保留既有有效结论，依据历史快照与当前代码核验修复及直接回归。调用声明的报告输出优先于默认文件名；禁止覆盖调度维护的输入快照。
- 最终回执：最终回复以 FINAL_ANSWER 开头，随后只输出一个 JSON 对象；含标记、JSON 和空白在内最多 2048 个字符，中文按字符计，可以更短。禁止粘贴日志、源码、文档正文或完整 issues 列表。
- 必填字段：status、summary、outputs。outputs 为名称到已写入文档路径的对象，只列调用声明的输出；相对路径以调用指定的项目根目录为基准。详细问题见审核报告，不能因回执限长删减报告问题。
- 分析、拆分、开发、规范化、记忆整理和总结完成使用 completed；评审使用当前阶段允许的 approved / changes_requested / requirement_change。blocked 仅在本阶段既有规则允许时使用，资源详情写报告，回执简述并给输出路径。
- 流程仅依据当前阶段允许的 status 和产物校验推进；approval_token 仅为可选补充说明，可省略、为 null 或空字符串，不参与流程判定。空回复、只出现批准关键词、非法或超长 JSON 不代表通过。
- 收到“回执补正”时只读取已有报告并重新输出合规回执，不重做业务任务。审核补正、启动或网络失败都消耗累计审核额度，最多 10 次，不能借重试重置次数。
