# Figma 访问与冷却规范

**Figma MCP 定点发现：** 本轮涉及 Figma UI 需求的拆分、分析、开发或审查，需要读取远程设计或判定是否降级时，先通过当前客户端的工具发现入口，对 `figma-android-mcp` 单独做一次定点发现（如使用 `GetDynamicTools`，按其实际参数指定该服务名/命名空间）。不能仅凭初始工具列表未出现、泛化搜索未命中，或 `plugin-figma-figma` 被禁用/需要登录，就认定该服务不可用。发现工具后按返回的实际工具名和参数，在本角色既有权限内读取设计；未发现或发现入口不可用时，记录本次发现方式、结果及已知错误，再按下述设计来源顺序处理，不猜测是鉴权失败或 MCP 冲突，也不把直接 REST 请求记成 MCP 调用。同一轮不重复发现；仅补正回执、整理记忆/总结或复审只复用有效证据时，不额外触发发现或全量检查。服务名称不改变当前项目的平台与资源输出约束。

**设计读取与 skill 执行：** 定点发现服务后，先读取当前任务适用的项目 UI skill、工具说明和 MCP 返回的 `_REQUIRED_RULES`；服务提供 `get_skill` 时按其实际目录读取对应实现规范。例如 Android 布局可使用 `get_skill("android-layout")`，高还原规范可使用 `get_skill("figma-android-mcp-skill")`，仅在当前平台适用且服务确实提供时调用，不把示例套到其他项目。分析提取设计与转换约束；Developer 在实现或迁移 UI 前自行读取并执行适用规范，不能以 Analyst 读过替代；Reviewer 核对实际执行与产物，不能以工具发现成功证明已读设计或遵循 skill。记录实际读取的 skill/规则来源及采用要点，无需复制全文。工具/skill 不可用如实记录并按已有本地依据继续；工具建议与当前明确需求或角色权限冲突时，说明冲突并遵循当前任务授权和设计要求，不机械套用“仅导出已标记资源”“未标记一律占位”等默认策略。

**读取去重与覆盖：** 本角色同一轮按 file key、node-id、设计版本和状态去重读取；一个完整节点响应可支撑多条 AC，父节点已包含所需子节点属性时不重复逐子节点调用。保留实际来源和覆盖关系，不按 AC 数量重复请求。同一组件不同状态必须各有依据，不能用代表态代替；版本变化、范围新增或证据失效时只补读受影响节点。历史记录仅标复用，不能冒充本轮 MCP 调用；复审沿用既有问题与直接回归范围。 完整文件 JSON/节点原始响应按版本缓存，禁止为每个页面重复 GET file；已有响应覆盖所需属性时直接复用。仅在工具实际支持多节点参数时批量读取或导出，不给单节点工具编造 `ids` 参数。

**请求节奏与冷却交接：** 本条限定全文远程读取要求，不扩大当前角色权限或复审范围。Agent 发起会访问 Figma REST API 的读取/导出默认串行，相邻远程请求至少间隔 7 秒；服务要求更长间隔时以其要求为准，不并行启动重复下载脚本或子任务。纯本地读取、工具发现和本地 skill 读取不机械等待；MCP 内部并发/重试不可见时如实说明，不声称已控制底层请求。读取前核对上游既有报告中的冷却记录；未到期先利用本地资料或推进其他可控工作。

**429 记录与重试：** 记录请求接口/文件/节点范围、发生时间、工具实际返回的 `Retry-After`、`X-Figma-Plan-Tier`、`X-Figma-Rate-Limit-Type` 及最早可重试时间，不输出 Token。工具未暴露响应头时标明不可得，不猜测或额外请求只为补日志；`high`/`starter` 不能单独证明具体配额，等待后仍受限不能直接断定其他程序占用。遵守 retry-after，冷却期内不得通过换节点、切换 MCP/REST/curl 渠道重试同一受限配额。响应头缺失时不得立即重试，采用串行退避或转本地资料；单次读取任务额外重试最多 5 次，不要求耗尽，服务已披露的内部重试计入，不能再叠加外层循环。冷却与已知重试次数写入本角色已有交付/审核报告供下游沿用，不能因角色接手重置；审核只记录自身报告，不修改物料或越权维护上游文件。
