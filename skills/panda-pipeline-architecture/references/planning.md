# 架构规划内容与模板

拆分判断项目阶段：根据当前原始需求及源码、模块、依赖与配置核实是否初始化。初始化项目按实际技术栈调研并在 shared_context.md 中规划；既有项目复用现有架构资料，缺失时补「现有架构分析」，仅说明本次影响，不默认推翻架构。简化流程只做当前需求的架构落位分析，不承担全项目初始化规划。

初始化规划至少覆盖以下内容，文档使用已有等价章节时可直接沿用。选择依据须可追溯，未验证的规划不能写成已有能力。UI 设计 Token 与资源操作依照 UI skills，接口字段与协议细节依照 Swagger skill，架构章节只登记责任与入口，不复制其明细。

```markdown
## 🏗️ 架构规划（初始化项目 · 架构师产出 · 后续 Agent 必须遵守）

### 1. 技术栈选型（含调研依据）
- 各平台/模块的编程语言、框架及版本
- 选型理由（引用官方推荐、社区趋势、项目适配性）
- 调研来源标注（URL + 调研日期）
- 禁止使用的技术及理由

### 2. 模块划分与边界
- 顶层模块/包列表及职责说明
- 模块间依赖关系（用 ASCII 图或文字描述，禁止循环依赖）
- 每个模块的公开 API 边界（对外暴露什么、隐藏什么）
- 新增模块的判断标准

### 3. 魔法值公共目录与常量治理（必做）
- 明确项目级公共目录的精确路径（如 `common/constants/` 或平台等价目录），由所有业务模块统一依赖
- 集中管理颜色、尺寸、间距、圆角、字体、动画时长、超时时长、重试次数、分页大小等跨模块复用值
- 规定常量文件/类型的命名、分组和访问边界；区分设计 Token、业务配置和环境配置，禁止混放
- 后续开发 Agent 必须先查找并复用该目录；目录不存在或缺少所需常量时，必须先补齐公共目录/常量，再实现业务代码

### 4. 分层架构
- 各层的职责定义（如 Presentation / Domain / Data）
- 层间依赖规则（如 Data 层不依赖 UI 层）
- 跨层通信机制（接口抽象、回调、Flow/Publisher/Combine 等）

### 5. 核心数据流
- 从用户操作到数据持久化的完整链路描述
- 状态管理策略（单向数据流 / 事件驱动 / 响应式）
- 错误处理与异常传播路径

### 6. 依赖注入策略
- DI 框架选型及理由
- 作用域设计（Singleton / Scoped / Transient）
- 模块化 DI 组织方式

### 7. 测试策略
- 测试金字塔：单元测试 / 集成测试 / E2E 测试的比例与工具选型
- 各层测试策略与 mock/fake 方案
- CI 中测试的执行策略

### 8. 命名与代码规范
- 文件/类/方法命名约定
- 目录结构规范（精确到二级目录）
- 代码风格与静态检查工具配置

### 9. 演进路线
- 当前阶段的技术债务预测
- 未来可预见的扩展点及预留设计
- 后续架构评审的触发条件
```

公共能力与复用边界、共享来源、物料入口和跨需求交接路径按 [共享上下文格式](shared-context.md) 维护，不在本模板另建第二份表。

架构约束作用于当前实际改动：模块边界、分层与依赖方向、选定技术栈、命名/目录、DI 及魔法值公共目录。开发先查找并复用既有常量和能力；目录及具名常量缺失时按当前开发权限补齐。规划自身不是新增模块、引入依赖或修改共享核心约束的授权；架构偏离按本角色现有分析、报告和需求修订路径处理。

演进路线只记录当前需求有依据的风险、可能变更条件和评审触发点，不要求提前实现未来扩展基础设施或为格式完整引入新的框架。当前需求已有明确约束时遵守该约束，不从示例推导目标平台或业务决策。
