# shared_context.md 格式与维护

## 文件定位与适用范围

唯一文件名为 `shared_context.md`，不另建 `share_context.md`。Break 默认位置 `requirements/shared_context.md`，实际以调用指定路径为准；它是本批次临时公共信息，随本轮目录归档，不是长期 memory，也不是任务执行状态的替代来源。原始需求决定项目类型、目标平台与技术栈，不把模板中的示例变成支持范围限制。

生产者按实际适用性建立以下章节；已有等价结构和稳定引用时增量补齐，不全量重排。未涉及 UI、接口或某平台时注明不适用，不制造空的 Figma/移动端交付物。下游只消费本项需要的信息，不以缺少无关章节阻断任务。

## 建议章节及必需内容

| 章节 | 需要保留的内容 |
|---|---|
| 批次来源与适用范围 | 原始需求/补充说明的可解析入口、来源版本或获取时间、当前范围、目标与技术栈依据；事实、规划和待验证的区别 |
| 全局上下文与验证环境 | 跨需求业务场景、明确限制、验收口径；实际环境/接口地址、账号凭据的来源与适用范围，缺失条件及可验证范围 |
| 架构规划 / 现有架构分析 | 初始化项目按架构模板规划，既有项目引用实际模块/分层/数据流/依赖；公共依赖顺序、框架/依赖/接口封装复用方向与长期维护注意事项 |
| 公共能力与复用边界 | 下方能力表、跨需求字段/方法归属、提供方和消费方的接入及验收责任 |
| 物料入口（涉及 UI 时） | 本批物料根、范围清单、每项 manifest 路径与路径解析规则；设计原件和资源转换责任只登记入口，详情维护在物料索引 |
| 接口与验证边界（涉及接口时） | Swagger/接口契约入口、公共协议提供方与消费方；后端接口与 mock 约束、实际可用环境和真实未验证范围 |
| 未决事项与交接入口 | 具体来源冲突/缺口、受影响需求与可继续部分、待补信息/补验条件；本轮 develop_urge.md 路径及维护责任 |

环境矩阵引用角色已要求的目标 OS/arch、宿主与工具链、实际授权入口、检查命令/结果、当前可验证范围、缺失条件及负责验收的需求 ID，不复制第二份相互漂移的矩阵。原始需求明确提供的测试环境、账号、密码和凭据须在本轮授权产物中保留其适用范围及可用入口，不编造或脱敏至不可用，不沉淀到 memory。每个相关小需求的「全局上下文」必须传递下游实际需要的信息及来源，不能只存在父对话、索引或不相关小需求中。

交付级别仍由需求与角色现有门禁决定：涉及 Android/iOS 的批次声明移动端默认上限 runnable，只有具有原始升级依据的目标可为 deployable；列明升级子需求和依据，无则写“无”。其他平台按实际契约与工具链，不套用移动端限制。此格式不授予发布、部署或其他外部操作权限。

## 公共能力与复用边界表

在架构章节维护唯一表格：

| 能力 ID | 能力与提供方需求 | 实现入口（路径/符号） | 已实现范围与未实现边界 | 消费方需求及接入责任 | 状态 | 证据 |
|---|---|---|---|---|---|---|
| 当前能力的稳定 ID | 实际能力与提供方 | 真实入口；规划位置须注明 | 分开描述可复用与仍缺少部分 | 消费方 ID、接入动作与验收责任 | planned / unverified / verified | 来源、源码、开发/审查报告及测试定位 |

只列当前项目涉及的网络、业务提交、H5、路由、存储、UI 等能力，不生成无关能力清单。跨多个需求的同一契约，在相关条目下按字段/方法记录来源、公共提供方、业务消费方及接入验收责任；已知与待确认字段分开，不能只列模块名。公共提交入口存在不代表业务 Step 已接入，H5 容器存在不代表业务参数/回调齐全。

- `planned`：仅规划归属或入口，尚无实现证据。
- `unverified`：已实现或本轮变更，但声明范围尚未独立核验。
- `verified`：有可追溯的审查与源码/测试证据，结论仅覆盖已核验范围。历史 verified 仅在证据仍适用时保留；Stub、文件存在或其他项 approved 不能替代核验。

拆分建立归属与计划；Developer 按授权仅更新本轮相关能力事实、标记 planned/unverified，不自行升级 verified；Code Reviewer 按授权仅更新已核验状态/证据，不改能力归属、需求内容或其他章节。分析和需求评审只读消费。修改使证据失效时记录原因和历史，只回退受影响部分，不清空其他 Agent 的记录。

## 物料入口格式

Break 默认在「物料入口」声明根目录 `.`，相对 shared_context.md 所在目录解析，运行时即 requirements/，随批次归档；列明 Figma 范围清单 `_figma_inventory.json` 及各 UI 小需求 `R-xxx-name/figma_assets/asset_manifest.json` 的实际路径。入口均相对 shared_context.md 所在目录，manifest 内文件路径相对所属小需求目录，不能依赖当前 Shell 工作目录或归档前绝对路径。

Figma 专项字段仅在采用 Figma 时适用；其他设计资料记录实际入口，不虚构 inventory 或节点。schema_version: 3、frames[].design_source、原始响应/参考图/原件映射及转换审计的具体格式由项目已安装的 `panda-pipeline-ui-assets` 维护；准备或核对这些物料时必须读取该 skill，不在 shared_context.md 复制整份 manifest、Token 或素材清单。

## develop_urge.md 交接说明

这里只登记 `requirements/develop_urge.md` 的实际路径和用途，与 shared_context.md 同级，由 Developer 首次产生本轮跨小需求接入事项时创建，随本轮目录归档。拆分阶段不创建、读取、维护或验收该文件；未产生事项而没有文件是正常情况，不补空文件、不恢复归档待办。稳定跨轮知识仍由现有 memory 流程承接。

交接条目的具体字段和写入授权沿角色的既有交接协议，不因共享文档模板增加写权限。能力表和交接表互相引用稳定 ID，不把提醒已登记当成实际接入完成。
