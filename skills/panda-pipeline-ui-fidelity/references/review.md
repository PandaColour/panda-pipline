# review 视觉验收

- **两类验证：** `逻辑` AC 按断言验证行为终点、状态流转、实际字段/请求及异常恢复，涉及权限、导航或设备交互时使用必要运行验证，不能一律降为单测。`UI` AC 实际查看同一页面/组件状态的设计与运行图，核对尺寸、位置、对齐、字体、颜色及素材；适配与外部文案差异按既有边界记录。报告沿用 AC 编号并注明类型、证据和逐条结论，不新增平行清单；首审覆盖全部适用 AC，复审仅查既有失败项、直接回归及失效证据，保留未受影响结论。

## 原始视觉 AC 与问题关闭

关闭视觉 issue 时，将“原始 AC 的视觉要求 → 本轮设计/运行对照 → 修复结果或具体残留”写在该 issue 下，不能只照开发改动清单逐项打勾。“示例区已补齐”还须检查示例内容正确；“图标已替换”还须检查原 AC 适用的尺寸、配色与位置。新增截图暴露同一 AC 的素材、布局或样式残留时沿用原 issue，不能以“本轮只修文案/补图”排除；不扩展到无关 AC 全量复审。原始视觉要求未满足时不得写“全部关闭”；合规外部降级结束当前审查时单列未通过/未验证事实，不计入视觉通过。

required_level 只是分析安排，不能覆盖原始 AC：发现视觉断言被设为 L1 时，指出验证安排不足，仍核对对应运行截图与设计基准；只有真实需求/契约修订才回流需求，补视觉证据或可实现差异交 Developer。首审把“缺截图/缺资源”问题绑定具体 AC 与关闭条件：证据有效且经实际对照支持该 AC，或已充分核实的外部缺口按既定降级交接。补图后发现该 AC 仍有布局、尺寸、素材或控件结构差异，是原问题残留，沿用稳定 issue ID，不要求证明差异由本轮 diff 引入，也不因补了文件就关闭。

已核实的外部缺口可结束本轮可控工作审查，但报告中的原始视觉结果继续保留未通过/未验证及原因；不能用“已修复”描述仅暂用低清图或临时替代的部分。实现可修复差异返回 changes_requested；不得将违背必须 AC 的差异降成 N/P 标签建议。复审只看原问题、人工反馈、直接回归和缺失/失效证据涉及的项，不重新全量检查。


## 实现核验与视觉对照

以下远程调用与 MCP 清单仅限 Figma 来源；非 Figma UI 按需求指定基准核对，不虚构节点或读取记录。

只对当前“必须”UI AC 的目标页面、目标组件和目标状态执行硬门禁。先逐项检查本地物料、字体、参考图和映射路径可读，再读取 Developer 的「Figma 远程读取记录」与「Token → 代码映射表」。首审且网络、权限和工具可用时，Reviewer 必须对当前 UI fidelity manifest 中的全部必要页面/状态/平台按节点与版本去重调用 `get_figma_node`；按基准的适用属性核对字体/字重/对齐、布局间距、图标尺寸/显示与有效图形边界、效果及裁剪；共享基准与代码映射只记录一次，不要求每条 AC 重复全套字段；远程数据与本地 Token、参考图或映射冲突时，**以远程 Figma 为准**。Developer 开发当时网络、权限和工具正常却**缺少远程读取证据**时，当前 UI AC 必须返回 `changes_requested`；不得把本地 Token、参考图或并排截图当作远程读取证据。只有网络不可用、权限/鉴权失败、`get_figma_node` 不存在或调用失败、node-id 失效或无法读取时才接受降级，并核对调用方式、真实失败信息、受影响节点和 UI AC、采用的本地资料及未验证范围；不得静默降级，部分节点成功时仅对失败节点降级。每个“必须”UI AC 还必须同时具备：引用的精确 Token、相关 Token 的代码对应（共享基准只记录一次）、Figma 原画或本地设计基准图 ‖ 目标运行环境的实现截图（如浏览器或 Simulator/Emulator）并排证据；缺少可由本地资料、实现或验证补齐的任一项即返回 `changes_requested`；真实外部缺口按公共缺口规范保留未验证并验收其余可控部分，不得降级为建议，也不得写 UI AC 通过。在 `test_report.md` 记录实际采用的远程/本地设计值及来源、实现值、差值、适用的原始阈值或结构/样式判据和结论。若设计设备不是基准宽度，还要核对适配公式已生效。不得接受“结构一致”“视觉接近”“差不多”“严重不符才失败”等主观结论；差值超过 UI AC 明确阈值即不通过。必要实现截图写入 `ui_review/actual_screens/`，并在 `test_report.md` 形成视觉对比表。无法达到目标运行证据时标记“静态验证”或“环境阻塞”，不得伪装通过。不得扩张到 AC 未提及的全部页面、全部组件或全部状态；非 UI 项、明确默认排除且不交付 UI 的关闭态需求不得要求截图。
   同时检查当前 AC 使用到的物料复用和重复导入：同一来源物料应复用同一工程资源，不得因远程读取新增重复下载、复制或实现。

## Figma MCP 使用清单审查（开发阶段）

检查 Developer 是否将分析中的业务步骤、最终字段/调用和设计基准落实到真实源码与运行结果，并执行适用 skill 的资源转换及核对要求。复用旧代码、字段已定义、清单勾选、资源审计 passed 都不能替代这一验证。特别检查实际消费资源的图形大小/位置/裁剪、文本对齐和字重；设计明确的错误不能以“未设阈值”降为建议。缺陷必须给出当前 AC、设计/实现证据及修改方向；允许多条 AC 引用同一有效基准或截图，不要求重复产物。

本节要求逐行保留覆盖结论，重复执行范围遵循本角色复审协议。Reviewer 必须检查 Developer 的「Figma MCP 使用清单」是否逐行覆盖全部当前“必须 UI AC”。开发当时网络正常且无有效复用记录时，未勾选项的理由不充分、清单漏项或把其他阶段的读取当作 Developer 证据，返回 `changes_requested`；开发当时网络断开或 MCP 真实失败时，只要对应节点本地物料审计通过、失败理由真实且影响与未验证范围完整，不因未勾选本身无限退回，可按本地基线完成审查。网络恢复或当前可用时，可对未勾选或可疑项独立调用 Figma MCP；发现必需资源遗漏时先按 `panda-pipeline-ui-assets` 的 code-review 模式按需补充下载并复审；外部权限/资源不可用按物料策略降级并继续其他工作；类型定义或需求范围确需修订时才按本角色允许的需求修订状态交回 Requirements Analyst。

## 当前平台 UI fidelity manifest（必须）

首审时 Reviewer 必须独立读取完整 `UI fidelity manifest` 和「页面/状态矩阵」，对需求明确的各个 UI 目标平台的每个页面/状态在远程可用时按节点与版本去重调用 `get_figma_node`，逐行核对相关必须 UI AC；失败节点按本地降级核验，不得仅抽样。检查 `business_canvas`、`platform_owned`、`external_asset/content`、viewport/safe area、当前构建截图或经核实仍适用的历史截图及实际对照证据，历史图保留原构建标识。

缺少可补的失败说明、状态/平台行、有效构建截图或实际对照记录，或只凭声明值声称“Token deviation 0”，返回 `changes_requested`；已核实的外部缺口按 [资源缺口](gaps.md) 处理，视觉结果保留未通过/未验证，不要求重复无效补验。P0/P1/P2 是 UI 偏差级别，不替代 AC 优先级和本角色阶段路由。P0 不通过；P1 修复或给出有依据的容差；P2 仅有具体平台差异证据且符合 AC 时接受。实现缺陷走 `changes_requested`；资料暂不可访问按来源降级处理，只有需改变原始范围/验收口径的真实需求修订才按本角色状态协议交接。这里的“抽检”只适用于非 UI 探索性检查，不适用于必须 UI AC。

复审按本角色既定增量边界逐行保留必须 UI AC 的结论及证据来源，只对受影响或证据缺失/失效的行重新执行远程读取与视觉验证；不得省略必要验收，也不得重复执行无关全量检查。

上述 `get_figma_node` 与 MCP 清单要求仅适用于以 Figma 为设计来源的当前 UI；其他设计来源沿当前需求基准核验，不虚构节点或 MCP 调用。首审覆盖本项必要 UI，复审按原问题、直接回归及失效证据限定重验范围，不因本规范中的“全部”重新全量验收。

物料审计和按需原件补充按 `panda-pipeline-ui-assets` 的 code-review 模式执行；不能仅因下载成功就通过，仍须核对工程引用、入包、实际显示与动效。源码、测试及工程资源修改交回 Developer；仅真实需求范围/类型修订按角色已有状态路由交回 Requirements Analyst。若本阶段允许 requirement_change 才使用该状态，不向简化流程新增状态。

`test_report.md`、代码审查报告为默认落点，以调用指定路径为准。可接受差异按 [设计来源与验收边界](sources-and-boundaries.md) 核实；图像与直接回归证据按 [视觉证据](evidence.md) 核对。
