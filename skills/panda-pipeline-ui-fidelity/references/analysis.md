# UI 精细分析与需求审核

## 当前项精细分析（analysis）

沿当前项物料入口读取 manifest → 原始节点/响应 → 参考图/原件/字体；在拆分范围内精细核对页面、组件和状态，补齐本项缺口，不重新精修整个批次。Figma 来源按 [来源规范](sources-and-boundaries.md) 的远程优先和失败节点降级执行，不能只凭截图推算已有精确属性。

精确视觉基准写入当前分析文档的既有「Figma Token 表」/UI 章节；物料映射只维护 manifest，分析引用其路径及相关节点。每个基准有页面/组件/状态、设计来源定位（Figma 使用 node-id）、版本、原始响应及参考图路径；按实际适用性提取设计画板、布局层级、宽高、gap、padding、offset/外边距、字体家族/字号/行高/字重/字间距/文本对齐、颜色/透明度/渐变、描边/圆角/阴影/裁剪、图标尺寸（逻辑显示尺寸）与有效图形边界、原件/字体路径和复用入口。核对嵌套属性，不能把 anchorMargin 当 padding、把未解析值写成设计没有。无此属性标不适用；读取不到才标缺失及影响。完整节点树保留原始文件，表中列实现所需值和状态差异，不逐 AC 重抄全树。

保留精确值与来源，不写“约”“某色系”“大致”。适配方案依据设计约束和项目实际布局机制，说明设计基准宽度、目标 viewport、固定/自适应尺寸及字号缩放策略；不强制将所有尺寸乘统一比例，不把 `375` 或 `Open Sans` 当通用默认。每条“必须”UI AC 引用实际相关的基准并给出可执行失败判据；原始数值阈值保留，无阈值时按明确设计值、结构/样式语义和有依据的平台差异判定，不强制发明 P0/P1/P2 数值容差。图标缩成小点、指定字重未使用、文本对齐错误不能因“没有阈值”放过。平台字体渲染、系统栏等例外需具体证据，不能统一豁免业务区域。

同一基准内已说明的适配与验证方法由相关 AC 引用；不重复生成数值表，不以表格填满代替源数据核对。

没有 Figma 链接、节点信息、API 或访问权限时，记录远程不可读取的原因并核查本地设计；只有本地也缺少对应资料时才按项标记“无法获取参考图”或“精确 Token 缺失”。本地证据已经充分时继续精细分析，不因远程暂不可用阻塞可控部分。

## UI 验收安排

验收安排须同时保留素材内容/用途正确与外观匹配两类要求；区域存在、文件数齐或审计 passed 不能作为视觉关闭条件。沿用既有 AC 与物料表记录来源节点和目标组件/状态，不增加一套平行台账。明确系统区域、动态数据和需求覆盖设计的有据例外；工程阶段按页面/状态交接证据版本及有效性，允许有依据地复用未受影响旧证据，禁止引用已声明失效的截图判通过。

原始 AC 包含布局、尺寸、字体、图标/素材、颜色或设计一致性断言时，验收安排必须包含对应设计基准与目标运行界面的实际查看和对照，不能以 L1 单测/代码检查覆盖视觉部分；使用 L1/L2/L3 时，这部分至少需要对应视觉断言的 L2 运行证据与对照结论，不能用无关的 L2 测试代替。已有拆分时，分析沿用上游 AC 编号和类型，分别安排逻辑验证与 UI 对照；简化流程在当前需求文档内生成逻辑/UI 分类与独立编号，保留来源映射及全部断言。遇到历史旧类型或混合项，只在分析中注明原类型及按断言对应的逻辑/UI 验证分项，保留原编号、全部断言和独立结论；不改写拆分文件，不因分类兼容新增业务范围。需求阶段只交付此安排，不提前要求 Developer 的截图。逻辑 AC 按行为终点、状态/字段和异常选择充分证据；权限、导航或设备交互仍需相应运行验证，不能因标为逻辑就一律只安排单测。没有数值容差时保留设计值与可判定的差异标准，不杜撰阈值，也不把明显控件结构变化放宽为通过。

在当前分析文档复用既有 UI/物料表，按 AC/状态写明可还原属性、真实缺口、目标组件/资源用途、开发自检与 Reviewer 对照标准。保留已有节点和跨项归属；不要从 Token 概要推导默认组件可以替代完整设计。原件与最终工程文件分开记录，工程转换、入包及运行核对由 Developer 实施。

## 当前平台 UI fidelity manifest

`UI fidelity manifest` 是既有 UI 基准的页面/状态矩阵与证据索引，不另建一套重复台账。覆盖当前需求明确的目标平台和每个页面/状态，记录 viewport、适用的 density/scale、系统栏/safe area，引用相关 AC、Token、原始响应、参考图及调用结果。多条 AC 共享基准时引用同一行；不同必要状态不得仅抽样。

按实际区域区分 `business_canvas`、`platform_owned`、`external_asset/content`；业务画布按当前需求指定来源；Figma 来源以远程 Figma 为准，远程不可用时使用已核实的本地依据，记录失败节点、采用值和未验证范围。P0/P1/P2 可沿用已有偏差分级，不要求给每行另造阈值。这里只安排后续代码与运行截图证据，分析阶段不要求已有实现或运行截图。

## 物料生产与写入边界

按 `panda-pipeline-ui-assets` 的 analysis 模式准备图片物料、字体、原始响应和参考图，补充后执行当前项审计。允许补齐当前 R-xxx 的 `figma_assets/`、`asset_manifest.json`、物料映射表和 Token 表，禁止修改其他 R-xxx；没有 R 编号的简化流程以调用指定的当前需求目录为作用域，不创建虚构 R 项。审计已通过才可声明对应资源完整；本地物料不完整时交接具体缺口，不将整项分析停止。

分析写入调用指定文档：Break 小需求为 `requirements_analysis.md`，简化流程为 `user_requirements.md`；UI 基准写入其中既有章节，物料映射只维护 manifest，引用路径与相关节点即可。

## 需求审核（requirements-review）

核对上面的精确基准、视觉安排与矩阵，审查只读，不执行 analysis 模式的生产写入。

对照原始需求核对视觉断言有没有被分析表降为单测、静态代码或“截图存在”；有此缺口返回 changes_requested 给本阶段生产者，不能只检查 required_level 枚举合法。检查缺失资源是否有具体来源/版本、已查资料、可实现属性和临时边界，不因数量少机械退回，也不接受把所有视觉项统一标待补。补充资料后继续检查它是否支撑原 AC，不能仅确认文件已生成。

逐项核对上述当前项基准是否精确、可读、有来源，必须 UI AC 是否绑定正确页面/状态和 Token；检查原始响应中的嵌套 padding/offset/字体/效果，不能只检查表格字段存在。可执行验证需指出前置状态、动作、观察对象、预期值与判据；仅写“截图对比”不充分。网络正常时缺少必要远程读取证据属于可修复缺口；真实失败则核验本地依据、降级范围与未验证事实，不要求反复恢复服务。

按 ui-assets 的 requirements-review 模式只读独立核对物料并运行当前项审计，允许写审查/审计报告，禁止修改原件、manifest、需求或源码；可修复遗漏返回 changes_requested 给 Requirements Analyst。只审核当前阶段资料与后续验收安排，不要求尚未实现的运行截图、Token → 代码或工程入包产物。复审仅核验原问题、直接影响项及失效证据，保留其余结论。
