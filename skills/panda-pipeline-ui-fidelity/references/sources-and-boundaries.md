# UI 设计来源优先级与验收边界

本规范适用于当前需求的 UI；目标平台、技术栈与交付等级由需求和仓库事实确定。Web/H5 使用浏览器 viewport，移动端使用 density/scale、safe area，其他 UI 使用实际运行环境。不把 Android/iOS 示例当白名单，不要求无 UI 的后端/命令行任务准备设计资料。

## 设计来源与读取

本节限定全文的持续推进、Mock 降级、渐进式交付、视觉一致性和通过条件，不扩大原始 UI AC：**优先 Figma MCP → 其次利用已有本地设计资料做高还原 → 两者仍不足时才对受影响部分先完成业务功能。** 前置工程依赖可以先建设；进入 UI 相关需求后，不得把已有依据的视觉实现统一后置为最后打磨。

远程读取遇到 429、权限或工具错误时，记录真实失败、受影响节点及重试条件；不要求一直等待配额恢复或耗尽重试。随后实际读取已保存的节点 JSON/原始响应、设计 Token、参考图、资产/字体及映射，核实节点、版本、路径和适用范围，按本地资料继续高还原。仅检查文件存在或哈希不算利用设计资料；不得因 MCP 暂不可用把本地已明确的渐变、字体、间距、描边、阴影或状态差异推迟到配额恢复后。局部缺口只影响对应字段/节点，其他已有依据的视觉与业务继续完成。

涉及 Figma 时，远程数据与本地 Token、参考图或映射冲突，以远程 Figma 为准；只有网络、权限/鉴权、工具或节点读取实际失败才允许降级；仅对失败节点降级，保留真实失败记录，不静默切换整个需求。

## 验收原则

来源降级不降低视觉标准。只有核实本地资料仍不足并记录具体缺失字段、查找/补充动作、影响 AC 后，才允许该部分先交付可控功能；UI 缺口保留为未完成/未验证，不能凭 runnable、Mock 通过、审计通过或风险披露写成视觉通过。开发提交后，本地依据足够但未实现或未对照属于可修复遗漏，代码审查应返回 changes_requested；外部缺口按本阶段既定路由处理，不反复要求恢复外部环境。无设计稿的原始需求按其约定设计与验收，不编造 Figma 基线。

## 可接受差异：屏幕适配与服务端文案

实际设备/viewport 比例、系统安全区或真实接口文案与设计样例不同，直接造成的合理布局适配、换行和内容长度差异，不单独阻断交付；Developer 可完成本轮交付，Code Reviewer 核实后可通过。无需为匹配样例修改真实业务文案、强行拉伸界面或更换设备；原需求明确指定的设备、文案、适配行为仍须满足。

拆分保留原始范围与设计入口；分析明确有依据的适配规则和动态文案来源，在既有 AC/设计基准中引用，需求评审核对口径，不提前要求运行证据。固定尺寸按设计单位与 density/scale 核对，自适应尺寸按边距/宽度约束核对，位置按对齐与锚点关系核对，不要求不同屏幕的绝对像素坐标或行数相同。没有依据时记录待核实项，不临时编造容差。

例外只覆盖直接受影响部分，不豁免文字裁切、控件重叠、操作不可达或无关的对齐、字重、图标、颜色与布局遗漏；不能整页免检，也不能为放行反向编造适配规则。真实相机内容、测试数据及系统区域同样按来源核对，不要求逐像素相同；资源缺失仍按 [资源缺口](gaps.md) 保留未完成/未验证。

## 差异关闭与复审

Developer 在既有报告记录设备参数或服务端文案来源、受影响区域、适配结果和运行证据；Reviewer 核实因果关系后记录“已接受差异”及依据，可关闭仅由此差异构成的问题，无需人工逐项批准。接口/已约定数据契约可作来源，Mock 须标明，不能将自行编写的占位文案冒充服务端结果或把 Mock 写成真实联调。已接受差异不计为未完成或未验证；未经核实的差异仍保留待验证。复审复用仍有效的结论，仅在相关设备条件、文案来源、代码或设计变化使证据失效时重查受影响项。
