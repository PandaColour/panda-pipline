# development 视觉验收

- **两类验证：** `逻辑` AC 按断言验证行为终点、状态流转、实际字段/请求及异常恢复，涉及权限、导航或设备交互时使用必要运行验证，不能一律降为单测。`UI` AC 实际查看同一页面/组件状态的设计与运行图，核对尺寸、位置、对齐、字体、颜色及素材；适配与外部文案差异按既有边界记录。报告沿用 AC 编号并注明类型、证据和逐条结论，不新增平行清单；首次交付自测覆盖全部适用 AC，返工验证既有问题、改动直接影响项及失效证据，复用未受影响的有效证据。

## UI 自检与返工完成条件

返工提交前，在原 issue 下核对“原始 AC 的视觉要求 → 当前设计/运行对照 → 修复结果或具体残留”，不能只报告新增了示例区、换了图标或改了文案。素材内容错误须修正，颜色、尺寸、位置等按原 AC 适用要求核对；无法满足的部分明确保留，不声称该视觉 issue 已全部修复。

首轮按当前必须视觉 AC 核对设计与运行结果，不能等 Reviewer 指出后才做视觉自检。返工按原 issue 对应的完整 AC 验收，不把“补截图/补物料”缩减为生成文件：补充后实际查看并修复有本地依据的视觉差异；仍无法解决的具体外部资源/清晰度缺口，沿原 issue 在 develop_report.md 保留事实、临时处理和补验条件。不得因上轮列为建议而把已证实违背必须 AC 的差异写成通过；无 AC 依据的美化建议不扩大本轮工作。

## 开发实现与自测（仅当前“必须”UI AC 适用）

开发前先读当前分析的业务步骤、依赖接入、设计基准、资源用途及验收方法，核对源码真实能力；不能跳过精细分析，直接复制旧实现后只修到构建通过。复用旧页面/素材也须核实当前设计版本、状态、实际消费文件、显示尺寸、有效图形边界和转换链路；已验证匹配的可复用，不为形式重导出。缺失时按当前作用域补齐，错误切图须从原件重新转换。

以页面/状态/组件为单位实现并自测：业务入口与最终请求/结果贯通，设计值落实到实际布局、字体、文本对齐和资源显示。每个独立基准记录一次 Token → 代码映射，多条 AC 引用同一行；同状态的有效并排图可支撑多条 AC，不能拿另一状态或无关测试代替。报告中的远程读取记录、Figma MCP 使用清单和 UI fidelity manifest 可互相引用，不重复复制同一响应或矩阵。

设计读取执行 [设计来源规范](sources-and-boundaries.md)，取得当前页面/组件/状态的结构、布局、尺寸、字体、效果与资产引用后再实现；同时逐文件验证本地物料、字体、参考图和映射路径可读且可入包。不得只凭截图目测代替已有精确设计数据。以下要求适用公共来源规范的可接受差异和关闭规则。

1. **只复用统一视觉底座：** 开发前扫描仓库已有的设计系统、基准宽度缩放函数、字体注册、颜色/圆角/间距 Token、背景效果和同类组件。相同视觉语义必须复用同一样式或组件入口，禁止页面各写一套 magic number。设计基准宽度、字体家族以设计来源为准，适配方式结合设计约束与项目布局机制，不机械统一缩放；例如某项目可以是基准宽度 `375`、字体 `Open Sans`，但不得把示例值套到其他项目。
2. **字体和资产必须入包：** Token 指定的字体文件和关键资产必须注册或导入工程资源。未经需求变更，不得用 systemFont、近似字体、近似图标或占位资产静默替代。
3. **远程读取与 Token → 代码映射：** Figma 来源的 `develop_report.md` 必须增加「Figma 远程读取记录」，逐项记录目标页面/组件/状态、node-id、调用方式与结果、数据来源、本地值、远程值、采用值、失败或降级原因、受影响 UI AC、采用的本地资料和未验证范围；所有当前 UI 实现同时增加「Token → 代码映射表」，逐行记录 Token 项、精确设计值、代码文件/行或符号、统一样式/组件入口、实际实现值和偏差。每个当前“必须”UI AC 引用的 Token 行都必须有代码对应；缺少映射时不得声称已完成视觉对齐。
4. **物料按需补充：** 按 `panda-pipeline-ui-assets` 的 development 模式只读运行审计、补充当前原件并重新审计，再按实际平台规范转换入包；外部缺口按公共缺口规范继续可控部分。
5. **并排视觉自测：** 将对应设计基准图与目标运行环境的实现截图（如浏览器或 Simulator/Emulator）生成并排对照，保存到当前需求目录 `ui_review/`，并在 `develop_report.md` 引用。首轮覆盖每个当前“必须”UI AC 的目标页面/组件/状态；返工仅补充受影响或缺失/失效证据项。优先选择设计基准宽度的设备；使用其他尺寸时必须同时给出适配公式已生效的证据。已有仍有效的并排图可引用复用。没有并排图不得写“视觉对齐通过”，只能标记未验证或环境阻塞。
6. **按设计值与可执行差异判据自测：** 逐项核对 UI AC 规定的字体、基准适配、间距阈值、控件几何和关键效果裁剪范围。明确尺寸、字重、对齐或资源用途错误必须修复，不能因无数值阈值而放过；平台差异需具体依据，不得以“结构一致”“看起来接近”“差不多”替代实际核对。非 UI AC、明确默认排除且不交付 UI 的关闭态需求不适用本节，不要求截图。

## Figma MCP 使用清单（开发阶段）

以 Figma 为设计来源的当前 UI 小需求，必须在 `develop_report.md` 增加「Figma MCP 使用清单」，按页面/组件/状态列出当前全部“必须 UI AC”的关联，不生成 AC 与全部节点的组合；同一成功调用可由多行引用，不得只列实际调用过的节点。表格至少包含：`UI AC | 页面/状态 | node-id | get_figma_node | 结果/失败原因 | 本地基线 | 影响与未验证范围`。

`get_figma_node` 栏打勾（✅）只表示**当前 Developer 阶段实际成功调用**；Requirements Analyst、Breaker 或其他阶段的调用记录不得代替本阶段证据。首次开发未勾选（☐）必须写真实的网络、权限、工具或 node-id 失败原因；“本地物料够用”“之前其他阶段已经读取”“时间不足”不是合法理由。修复轮次可引用本 Developer 先前仍有效的节点读取记录并标记来源轮次/复用，不伪称本轮重新调用；仅对设计变更、受影响或证据失效的节点重新读取。

网络正常时，当前“必须 UI AC”对应的每一行都应成功读取；缺少行、无结果或无合理失败原因不得声称 UI 完成。网络断开时，逐节点核实本地 `figma_asset_audit.py` 审计已通过的范围，每个未勾选项记录失败信息、本地采用资料、影响和未验证范围；已有依据部分按本地基线继续，缺失部分不能宣称资源完整或视觉通过；不得静默降级。

## 当前平台 UI fidelity manifest（必须）

开发前必须读取当前需求的 `UI fidelity manifest` 和完整「页面/状态矩阵」，确认需求明确的各个 UI 目标平台、viewport、safe area 及每个状态的设计来源定位（Figma 使用 node-id）。以 Figma 为设计来源且网络、权限和工具正常时，对必要页面/状态和目标平台按节点与版本去重调用 `get_figma_node`，覆盖相关必须 UI AC，不得仅抽样；逐行写入 `develop_report.md` 的「Figma MCP 使用清单」。

实现必须区分 `business_canvas`、`platform_owned`、`external_asset/content`，业务画布复用共享 Token，按既定规则适配屏幕/viewport、系统安全区、原生控件和渲染差异，服务端动态文案按 [设计来源与验收边界](sources-and-boundaries.md) 中的可接受差异规则核验。每个页面/状态/平台保留当前构建截图或经核实仍适用的历史截图，并与对应状态的设计基准比较（Figma 来源使用对应 Figma 状态）。历史截图保留原构建标识；返工仅为受影响或缺失/失效证据项重采。P0 阻塞交付，P1 修复或记录明确容差，P2 仅有具体平台差异证据且符合 AC 时接受；不得以声明值或“Token deviation 0”代替截图证据。失败节点只能按本地基线降级，并记录失败节点、理由和未验证范围。

## 委派 UI 工作

委派前将本 skill 在当前工程的绝对路径、`development` 模式、当前分析基准/manifest 入口、目标 AC/页面/状态和输出范围交给子 Agent；不能假设它继承父 Agent 已读的规范。父 Agent 对交付仍负责，合并后核对真实消费资源、Token → 代码、视觉对照与残留，不以子 Agent 的 completed 代替自检。

报告以调用指定路径为准，`develop_report.md` 为默认名；表格与证据互相引用，不重复创建完整清单。验收和证据规则见 [视觉证据](evidence.md)。
