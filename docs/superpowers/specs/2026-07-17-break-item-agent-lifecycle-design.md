# Break 小需求 Agent 生命周期与记忆整理设计

## 目标

Break Pipeline 在每个小需求中保留连续对话上下文，但不会在跨小需求时累积 Agent；每个小需求在完成功能、测试和审核后，先整理可复用记忆，再标记完成。

## 生命周期边界

首次选择某个未完成小需求时，流水线为该需求创建一套专属 Agent：需求分析、需求评审、开发、测试、代码审查和记忆整理。该套 Agent 仅服务该需求。

需求评审、人工需求审核、代码审查、测试或人工代码审核的返工，都继续使用该套 Agent，因此能保留该需求的反馈和决策上下文。只有该需求完成记忆整理并成为 `已完成` 时，流水线才释放这套 Agent。

进入下一个小需求时，重新创建一套 Agent。跨小需求不得复用 Agent 或会话；跨需求共享信息只能来自 `memory/`、前置需求正式产物，以及当前需求目录内的文件。进程重启后，内存会话无法恢复，流水线为未完成的当前需求创建一套新 Agent，并由正式文件恢复上下文。

## 流程与状态

每个小需求按以下顺序执行：

```text
待需求分析 → 需求分析 → 需求评审 → 需求人工确认 → 待实施
→ 开发 → 测试验收 → 代码审查 → 代码人工确认
→ 待记忆整理 → 记忆整理中 → 已完成
```

代码人工审核通过不再直接设置 `已完成`，而是设置 `待记忆整理`。记忆整理 Agent 成功写入当前小需求的 `memory_report.md` 后，才设置 `已完成`。重启时 `待记忆整理` 与 `记忆整理中` 都可恢复并仅执行记忆整理。

## 记忆整理

新增 `item_memory_curator.md`。它只能读取当前小需求目录中的 `user_requirements.md`、`requirements_analysis.md`、`develop_report.md`、`test_report.md` 和 `code_review.md`，以及现有 `memory/`。

它在当前目录写 `memory_report.md`，其中列出：提取的可复用事实、写入或更新的 memory 文件、未写入的临时信息及原因。仅记录经当前项实现和测试验证的架构、业务规则、接口、数据模型、Figma 资产复用规则、陷阱或场景；不得写入猜测、临时调试信息、密钥或无关内容。写 memory 前先维护 `memory/memory_index.md`，优先更新已有主题文件。

用户已明确要求本流程进行记忆整理，因此该 Agent 具有在此阶段更新 `memory/` 的授权。

## 拆分阶段记忆

不再在结束时向所有 Agent 广播反思。全部小需求完成后，只创建或复用一个拆分 Agent，读取拆分索引和各小需求的 `memory_report.md`，进行一次拆分层面的记忆整理；它不重复逐项实现细节。

## 恢复与隔离

执行中的小需求在进程内由 `item_agents[requirement_id]` 保存。该条目只在当前小需求完成后删除。若该需求后来重新进入返工状态，仍复用同一组 Agent；如果进程已重启，则从各报告重建上下文。

`execution_plan.json` 的有效状态集合和索引规范化 Prompt 增加 `待记忆整理` 与 `记忆整理中`。旧 `pipeline.py`、其 Prompt 和状态机不变。

## 验收

- 同一小需求的返工使用同一 Agent 实例；不同小需求使用不同实例。
- 当前小需求完成后，其实例从缓存移除；后续小需求不会继承其会话。
- 人工代码审核通过后先进入记忆整理，写出该需求的 `memory_report.md`，再变为 `已完成`。
- 重启时，`待记忆整理` 或 `记忆整理中` 的需求只恢复记忆整理。
- 最终反思只调用拆分 Agent，不广播给所有小需求 Agent。
- 原有 `pipeline.py` 工作流不受影响。
